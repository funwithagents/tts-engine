# Idle deadline for the polling receive loops

**Status:** Done

Implements "Idle deadline" in `specs/modules/gradium.md` and in `specs/modules/elevenlabs.md` ("Text stream"): a server that goes silent once the whole text is with it fails the utterance after `timeout` instead of holding the engine's lock. Deepgram, Cartesia and OpenAI already bound that wait in their own way and are not touched; a silence while text is still arriving stays unbounded, by design.

## Scope

- `src/tts_engine/modules/gradium/module.py` — `_receive` becomes a method and raises `TTSError` after `timeout` without a message once end-of-stream is sent
- `src/tts_engine/modules/elevenlabs/module.py` — `_stream_input_chunks` does the same once the end-of-stream frame is sent
- `tests/modules/test_gradium.py`, `tests/modules/test_elevenlabs.py` — the deadline, and the two silences it must not count
- `specs/modules/gradium.md`, `specs/modules/elevenlabs.md`, `specs/tts-module-interface.md` — the rule; `docs/modules/gradium.md`, `docs/modules/elevenlabs.md` — the `timeout` rows

## Steps

1. **Gradium.** In `_receive`, keep `idle_since`, set at the top of the loop when it is unset and the text is complete (`sender is None or sender.done()`), cleared after each message. On a poll that wakes with no message, raise `TTSError` when `loop.time() - idle_since >= timeout`. Setting it at the top of the loop, after `callback` returned, keeps the sink's time out of it.
2. **ElevenLabs.** In `_stream_input_chunks`, an `end_sent` event set by the sender after the end-of-stream frame; the same `idle_since` rule in the receiver, checked in the `TimeoutError` branch before the keep-alive. The generator is resumed only when the decoder wants the next chunk, so the clock starts after the sink is done with the previous one.
3. **Docs.** The `timeout` rows of the two module pages say what the field bounds; the shared sentence was wrong for both.
